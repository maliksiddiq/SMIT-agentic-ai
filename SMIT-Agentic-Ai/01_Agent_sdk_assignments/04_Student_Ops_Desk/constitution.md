# Constitution — 04_Student_Ops_Desk
This document is the highest authority of the project.  
It defines the non-negotiable rules that every line of code, every agent, every tool, every configuration, and every decision must obey.  
Violating any rule written in this constitution is considered a complete failure of the build — even if the feature appears to work correctly, even if the tests pass, and even if the coding agent generated the code.  
These rules exist to protect the integrity of the system, the safety of student data, the correctness of the architecture, and the ability of the human owner to fully understand and defend the final product.
---
## 1. Project Identity
- **Official Project Name:** 04_Student_Ops_Desk  
- **Purpose:**  
  A student-facing operations desk that serves as the front door for all bootcamp-related questions.  
  A student asks a question in plain language. The Desk determines whether the question is about an assignment, a career path, or course administration. It answers using real course data, routes the conversation to the correct specialist when needed, refuses anything that is not related to the bootcamp, and closes every resolved conversation by producing a structured ticket.
- **Nature of the Project:**  
  This is a strictly specification-driven project.  
  The specification always comes before implementation.  
  Code is the last step, never the first.
- **Scope Boundary (Critical):**  
  All work must remain strictly inside the folder named `04_Student_Ops_Desk`.  
  No source files, configuration files, data files, or documentation may be created outside this folder.  
  Creating anything outside this folder is a direct violation of the constitution.
---
## 2. Development Process Rules (Highest Priority)
These rules govern how the project is built. They override convenience, speed, and agent suggestions.
1. **Specification before any code**  
   No source file of any kind may be written until Phase 0 is fully complete.  
   Phase 0 consists of exactly four documents:  
   - `constitution.md`  
   - `spec.md`  
   - `plan.md`  
   - `tasks.md`  
   These four documents must be written, reviewed, and committed to Git before the first line of implementation code is created.
2. **Git history is the official evidence**  
   The Git commit history will be examined as part of the evaluation.  
   A single commit that contains both specification documents and implementation code is an automatic failure of Phase 0.  
   The history must clearly show that the four Phase 0 documents were committed first, and only after that did implementation commits begin.
3. **The coding agent writes code. The human owns every line.**  
   The coding agent is allowed to generate code.  
   However, the human remains fully responsible for every single line that is committed.  
   If the human cannot explain a piece of code, that piece of code is considered unfinished — even if it runs without errors.
4. **No unreviewed commit is allowed**  
   Every diff generated by the coding agent must be carefully read and understood by the human before it is committed.  
   Committing code that the human has not fully reviewed and cannot explain is a direct violation of this constitution, regardless of whether the code works.
5. **Requirements are numbered and must be testable**  
   Every Functional Requirement (FR) and every Non-Functional Requirement (NFR) must be demonstrable on demand.  
   Saying “it should work” or “the code looks correct” is not acceptable.  
   The owner must be able to show the requirement working in a live run.
6. **Time is real, and cuts follow the official order**  
   When time runs short, features must be cut strictly in this order:  
   1. First cut FR-11 (custom runner).  
   2. Then cut FR-6 (Summariser-as-tool).  
   3. Then cut the AgentHooks half of FR-10.  
   FR-7 (Structured Ticket) and FR-8 (Input Guardrail) may never be cut under any circumstances — the viva is built on them.  
   Cutting from anywhere other than the top of this list — for example, cutting whichever feature is hardest — is a violation of this constitution.

## 3. Model & Provider Rules
1. The only model that may be used in this project is **`gemini-3.6-flash`**.  
   No other model is permitted under any circumstances.
2. The model must be accessed exclusively through an **OpenAI-compatible client**.
3. The model must be configured **at the agent level**.  
   It must not be set globally.  
   It must not be set per individual run.  
   Each agent must carry its own model configuration.
4. The function `set_default_openai_client` (or any similar global default-setting function) is completely forbidden.  
   It must never appear in any file of the project.
5. Every agent must explicitly declare its own model settings.  
   Nothing is allowed to generate text without a declared model and a declared ceiling.
6. The program’s main entry point must be an asynchronous function that is started using `asyncio.run`.  
   Synchronous entry points are not allowed.
---
## 4. Secrets & Configuration Rules
1. All secrets — including API keys, tracing keys, and any other sensitive values — must live **only** inside a `.env` file.
2. The `.env` file must be listed in `.gitignore` and must never be committed to the repository under any circumstances.
3. If a required key is missing, the program must fail immediately at startup with a clear and human-readable error message.  
   A deep, confusing stack trace caused by a missing secret is not acceptable.
4. No secret may ever be hardcoded in source code, comments, documentation, or configuration files other than `.env`.
---
## 5. Student Data, Context & Prompt Rules
These rules protect student privacy and enforce correct use of local context.
1. Student identity information (name, roll number, tier, etc.) must **never** be written directly into the system prompt as free text.
2. Student data may reach the model in only two allowed ways:  
   - Through deliberately written dynamic instructions that are constructed at request time, or  
   - Through tools that read the data from local context.
3. A `StudentProfile` object must be passed into every run as **local context**.  
   This is mandatory.
4. Any tool that needs student information must read it from the local context.  
   The automatically generated tool schema must **not** contain a wrapper parameter for the student profile.
5. If the entire source code is searched (using grep or similar) for a student’s real name, roll number, or tier, those values must appear **only** in the exact place where the `StudentProfile` object was created.  
   Finding them anywhere else is a violation.
6. **The system prompt is never static.**  
   The Desk’s system prompt must be dynamically constructed at the moment of each request using the current `StudentProfile`.  
   At minimum, the prompt must:  
   - Greet the student by name  
   - Mention the course the student is enrolled in  
   - Become noticeably shorter and more concise when the student has 3 or more open tickets  
   Using one fixed system prompt for all students is strictly forbidden.
7. **The fully resolved prompt must be inspectable.**  
   It must be possible to print or log the complete, final system prompt **before** any model call is made.  
   A prompt that cannot be shown before the model is called is a violation of this constitution.
---
## 6. Tool Rules
1. Tools are forbidden from raising exceptions to the caller (whether the caller is an agent or the runner).  
   If a tool encounters bad data or any failure, it must return a clear, useful sentence that the model can understand and act upon.  
   Raising an exception is considered a defect.
2. All course knowledge must live in a file named `courses.json`.  
   The agent may access this knowledge **only** by calling tools.  
   Direct access to the file from the agent’s prompt or instructions is forbidden.
3. The agent is strictly forbidden from inventing any course ID, assignment ID, schedule, policy, or other course data that does not exist in `courses.json`.  
   If a student asks about an assignment that is not in the file, the system must decline — it must never invent an answer.
4. Tool availability may be controlled by the student’s tier.  
   At least one tool must be available only to students with the “scholarship” tier.  
   For all other students, that tool must be completely **absent** from the list of available tools.  
   It is not enough to refuse the tool at runtime — the tool must not even be offered.
5. There must be a tool named `close_ticket`.  
   When this tool is called, the run must end immediately.  
   The output of this tool becomes the final result of the run.
6. Every run must have a hard turn ceiling.  
   Infinite loops or unbounded generation are strictly forbidden.  
   Exceeding the turn ceiling must raise an exception that is caught and reported cleanly.
---
## 7. Agent & Handoff Rules
1. The Assignments specialist and the Careers specialist must both be created by **cloning** a single base agent.  
   They are allowed to differ only in their instructions and their model settings.  
   The model configuration of the base agent must be shared and must not be restated in the specialists.
2. When a handoff occurs, the specialist that receives the conversation becomes responsible for answering the student.  
   The Desk must not answer after a handoff has taken place.
3. One specialist (the Summariser) must be exposed to the Desk as a **tool**, not as a handoff.  
   This ensures that the Desk remains in control of the conversation and continues to speak in its own voice.  
   After the Summariser is used, the final message to the student must still come from the Desk.
4. After any run finishes, it must be possible to identify in code exactly which agent produced the final answer.
---
## 8. Output & Structured Data Rules
1. Every successfully resolved conversation must produce a **typed** `Ticket` object.  
   Free-form text or plain dictionaries are not acceptable as the final output.
2. The `Ticket` must be defined as a Pydantic `BaseModel` with the exact required fields.  
   The final output of a successful run must satisfy this condition:  
   `type(result.final_output) is Ticket`
3. The `resolved` field of the Ticket must be used in real Python control flow (for example, inside an `if` statement).  
   Simply printing the value or leaving it for a human to read is not sufficient.
4. If a request is deliberately impossible or produces malformed structured output, the system must surface the official structured-output parsing error from the SDK.  
   Silently accepting a half-filled or invalid Ticket is forbidden.
---
## 9. Safety & Guardrail Rules
1. An input guardrail must examine every incoming question **before** the Desk’s model is called.  
   Any question that is not related to the bootcamp must be rejected by this guardrail.
2. When the guardrail rejects a question, the program must catch the exception and reply to the student politely.  
   The program must never crash because of an off-topic question.
3. A rejected off-topic question must cost **nothing**.  
   It must be possible to prove from the trace that the Desk’s model was never called for that question.
4. The system is forbidden from inventing or quoting any course policy that does not exist in `courses.json`.
---
## 10. Observability, Cost & Lifecycle Rules
1. Every conversation must be fully traceable.  
   Tracing must be turned on and must be exported using the project’s own key.  
   Using default keys or shared keys is forbidden.
2. One complete student conversation must appear as exactly **one** trace.  
   Multiple disconnected traces for a single conversation are not allowed.
3. Run-level hooks must create an ordered audit timeline that records every agent that participated in the conversation, including any handoffs.  
   One student question must produce one clear timeline that shows the agents in the correct order.
4. Agent-level hooks must be attached to **exactly one** specialist.  
   Attaching them to zero specialists or to more than one specialist is a violation.
5. A custom runner must wrap every run in the system.  
   This runner must stamp a unique request ID and record the elapsed time.  
   The custom runner must be registered only once, at application startup.  
   No agent definition is allowed to be modified in order to support the custom runner.
6. Every agent must operate under a turn ceiling.  
   If the ceiling is exceeded, an exception must be raised, caught, and reported cleanly.  
   Unbounded generation is forbidden.
7. The audit timeline created by the hooks must be written to a durable location (for example, a file or database).  
   Printing the timeline only to the console is not sufficient.
8. **Every span in a trace must be explainable.**  
   The owner of the project must be able to open any trace, name every span that appears in it, and point out at least one call that the Desk made which was not actually necessary.  
   An unexplainable span is considered an observability failure.
---
## 11. Interface Rules (Chainlit)
1. When the Chainlit interface is used, both the agent and the student’s profile must be created **only once** — at the moment the session starts.  
   They must not be recreated on every new message.
2. Conversation memory must be maintained for the lifetime of the session.  
   A second message from the student must be understood in the context of the first message.
3. Different browser windows or sessions must be completely isolated.  
   History from one window must never appear in another window.
4. The Chainlit message handler must use `await` with the asynchronous runner.  
   Calling the synchronous version of the runner is strictly forbidden.
---
## 12. Failure & Quality Rules
1. When a tool receives invalid or missing data, it must return a clear sentence that the model can understand and act upon.  
   Raising an exception that reaches the runner is a defect, not a feature.
2. Missing configuration, missing files, or invalid data must cause the program to fail early and with a clear message.
3. The system must remain stable when it receives off-topic questions, missing course data, or when a turn ceiling is hit.  
   Crashes under these conditions are not acceptable.
---
## 13. Absolute Prohibitions
The following actions are completely forbidden. Performing any of them is a direct violation of this constitution:
- Writing any implementation code before the four Phase 0 documents have been committed.
- Committing any code generated by the coding agent that the human has not fully read and understood.
- Using any model other than `gemini-3.6-flash`.
- Configuring the model globally or using `set_default_openai_client`.
- Storing secrets anywhere other than the `.env` file.
- Writing a student’s name, roll number, or tier directly into the prompt text.
- Using a single static system prompt that does not change according to the student profile.
- Allowing any tool to raise an exception to the caller.
- Inventing course data, assignment IDs, or policies that do not exist in `courses.json`.
- Offering a tier-restricted tool to students who are not allowed to see it (the tool must be absent, not merely refused).
- Returning free-form text instead of a properly typed `Ticket` as the final output of a resolved conversation.
- Allowing an off-topic question to reach the Desk’s model.
- Attaching agent-level hooks to zero specialists or to more than one specialist.
- Creating any file or folder outside the `04_Student_Ops_Desk` directory.
- Failing to make the fully resolved system prompt printable before the model is called.
- Producing traces that contain spans the owner cannot explain.
- Cutting anything other than the official cut order (FR-11 → FR-6 → AgentHooks half of FR-10).
- Cutting FR-7 or FR-8 under any circumstances.
